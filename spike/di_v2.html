Dependency injection without provider

The explicit dependency tuple on provider(Target, [deps], body) exists for one reason: the runtime sorted the graph before building anything. Build on demand instead and the tuple, positional injection, Plan, and the eight-level "undeclared dependency" diagnostic all go, while the flat list and the missing-service message stay byte-for-byte. Lazy initialisation costs one primitive, memo, plus a root-level lazy() for services that should not be built at boot, and no runtime mode.

Finding

The tuple only ever served the sort

Today a provider declares [Config, Logger] and receives them positionally. That tuple drives two things: the type-level Needs, and Plan.from, which runs Kahn's algorithm over the whole list before any constructor runs. The type level never needed it. gen already infers a body's dependencies from what it yield*s, and a provider body can be inferred the same way.

So the change is one decision: build services on first demand, memoised in the runtime, instead of in a pre-computed order. A yield* Db inside a provider body builds Db on the spot if it is not built yet. Cycles and missing providers still surface at startup, because the runtime demands every provider in list order.

Today
flat list→ Plan.from sorts→ build in order The sort needs every edge up front, so every provider writes its edges by hand, twice.
Proposed
flat list→ demand each, in order→ yield* builds on the spot Edges are discovered by running. Needs is inferred, and nothing can drift from it.

Everything downstream falls out of machinery that already exists. Check, MissingServices, the unordered list, "every service named once" and the diagnostic e2 exists for are all unchanged.

Two conventions carry the rest, and neither is API. First, interface Db and const Db live in the same file: type Db is the contract, value Db is the key, yield* Db gives a Db, and helpers take (db: Db). Measured in the prototype, type Db = typeof Db is never referenced and the …Api names are used only as parameter types, which is exactly what the interface now is.

Second, implementation-first for leaves whose shape is the value, and contract-first for anything with more than a couple of methods so hovers say Mps rather than a structural type.

Honest accounting The line count does not go down. Four yield* lines replace one tuple line, exactly as in the Effect version. What goes away is the triple bookkeeping between tuple, parameter list and body, two ceremony lines per service, and one concept. What arrives is the ability to put a dependency on a single method of a contract.

A contract can say, per method, what is needed at call time. A method that yield*s a service does not make it a construction dependency, so the requirement flows to exactly the programs that take that path.

Lazy initialisation

Once, on first read, with nothing waiting at startup

The case that decides how many laziness knobs exist: MPS reads from a local store backed by IndexedDB. Opening it is asynchronous, must happen once, nothing should wait for it at startup, the first read should wait, and later reads should find it open. MPS must not know.

Two mechanisms already cover "once". A provider body is an Fx, so an asynchronous open is already expressible as construction, and the runtime memoises every provider. The only thing missing is moving the sync point from construction to first use without leaking that into MPS's contract. That is one primitive.

Signaturememo
declare function memo<Value, Error, Dependency extends string>(
  effect: Fx<Value, Error, Dependency>,
  options?: { readonly eager?: boolean }
): Fx<Fx<Value, Error>, never, Dependency>
//  └─ the handle: dependency-free, because Dependency was recorded here, when memo was yielded
The scenarioservices/local_store.ts on IndexedDB
export const LocalStoreLive = LocalStore.make(function* () {
  const config = yield* Config
  // Opened once, on the first read, closed with the runtime.
  const db = yield* memo(
    acquire(
      () => openMessages('messages-' + config.userId),
      (store) => store.close(),
      (reason) => new IdbError(reason)
    )
  )
  return {
    get: (id) => gen(function* () {
      const store = yield* db                           // the read is the sync point
      return yield* fromPromise(() => store.get(id), (reason) => new IdbError(reason))
    }),
  }
})
// LocalStoreLive : Provider<'LocalStore', 'Config', never>     construction cannot fail
// LocalStore.get : Fx<Message | undefined, IdbError>           the open's failure belongs to the read
  • Yielding memo(fx) does not run fx. It records fx's requirements against the enclosing body, captures the current service map and scope, and returns a dependency-free handle.
  • Yielding the handle runs fx on first demand and joins every concurrent demand to that one run. Later demands get the value.
  • The run happens against the captured scope, so the acquire close registers on the runtime scope. A caller interrupted while waiting stops waiting and does not cancel a shared open.
  • Failure is not cached. Joiners receive it, the cell resets, the next read retries. Backoff is composition: memo(retry(policy)(open)).
  • { eager: true } starts the run in the background at construction. Reads arriving before it settles wait; reads after do not.
  • Outside a provider it captures the request. memo(db.query(id)) is one query per request however often the handle is yielded.

Send: a dependency needed only after the wire

send seals, transmits, then persists. MPS is needed only for the last step, and at the moment a send happens it may be unbuilt, or halfway through construction because Receive is building it. A service key is an Fx, so memo applies to it unchanged: the consumer says "later" in one line, and the resolution happens exactly where the code reaches for it.

Deferred dependencyservices/send.ts
export const SendLive = Send.make(function* () {
  const config  = yield* Config
  const crypto  = yield* Crypto
  const network = yield* Network
  const lazyMps = yield* memo(Mps)          // recorded in Needs now; resolved later
  let counter = 0
  return {
    send: (threadId, payload) => gen(function* () {
      const envelope = yield* crypto.seal(inbound)
      yield* network.send(envelope)
      const mps = yield* lazyMps              // empty → builds it · inflight → joins · done → returns it
      return yield* mps.ingest(inbound)
    }),
  }
})
// SendLive  : Provider<'Send', 'Config' | 'Crypto' | 'Network' | 'Mps', never>   the list is still checked
// Send.send : Fx<readonly Message[], DomainError>                                the contract is untouched
at yield* lazyMps
cell empty→Send's fiber builds Mps now LocalStore, PreStages and the rest are cheap; IndexedDB opens on the first put inside ingest.
cell inflight→Send joins Receive's build One construction, two waiters. No race, no second instance.
cell done→returns at once Every send after the first pays nothing.
Consequence for the surface No lazy mode on runtime: construction stays eager and in list order by default, which is what makes a bad graph fail at startup. Two ways to opt out, both the same cell. lazy(provider) at the composition root keeps a service out of the warm-up entirely, at the explicit price that its construction failure reaches the first demander as a defect. memo(Service) in a consumer defers that consumer's lookup without touching its contract. Whatever is expensive inside a service stays behind memo, at the granularity of the resource.
Runtime

One cell for providers and for memo

The runtime memoises providers with the same cell memo uses. resolve(name) is the cell for that name; memo is an anonymous one. One implementation, so construction and lazy init cannot disagree about joining, failure, interruption or teardown.

  • Startup demands each provider in list order. Cycles and missing providers surface exactly where Plan.from surfaced them.
  • The construction chain is inherited by fibers a provider forks, so a cycle that crosses a fork is still a cycle rather than a hang. This is the one genuinely new piece of fiber state.
  • Synchronous entry points do the same with a nested interpretSync; an async boundary inside a provider under runSync is Die(AsyncBoundary), as today.
  • Introspection improves: each provider can record what it demanded while building, so rt.graph() shows the graph that actually happened, including which conditional branches ran.

Trade-offs

Decide these with eyes open

of shares the instance across runtimes

LocalStore.of(new Map()) in two runtimes is one map. Same as Layer.succeed. Stateful doubles use make.

Conditional dependencies over-approximate

if (cfg.cache) yield* Cache puts Cache in Needs whether or not the branch runs, so the list must contain it. Correct, and the price of a static check.

Construction order changes

From Kahn order to list order, demand-first. Any dependency-respecting order is valid and teardown reverses whichever happened. A test that pins log order will move.

Defaults are never pulled in transitively

runtime([Send]) does not drag in Config. The check works on names, and a name cannot know whether it has a default. This keeps "named once" true and is the deliberate difference from Effect.Service's dependencies.

Mutual call-time dependencies declare the transitive set

ping needs 'Ping' | 'Pong', not just 'Pong'. The first draft got this wrong and tsc caught it, which is the point.

memo does not cache failure

A store that fails to open is retried by the next read. The opposite policy is a one-line change in the cell and should be decided once, for providers and memo alike, since they share it.

lazy trades fail-fast for one service

A provider wrapped at the root is not exercised at startup, so a construction bug in it is found by its first user, as a defect. Use it for services genuinely optional at boot, not as a default.

Deliberately not included

A plain-thunk overload for make. Generator-only keeps one form; of covers constants. Easy to add later if the function* with no yield* grates.

Decision

Go, and done

Implemented the same day. src/ now matches this page: service.ts, provider.ts, the new cell.ts, run.ts and memo in ops.ts; plan.ts is gone; the diagnostics fixture pins the new wording; the prototype is ported with memo(Mps) in Send and Receive and lazy() at its root, and its 27 scenarios pass unchanged.

The spike passes, the diagnostic e2 exists for is unchanged, runtime gains a check it was missing, lazy initialisation costs one primitive plus a root-level marker rather than a runtime mode, and the DI surface drops from twelve names to eight. The prototype port at the bottom of the spike compiles with the same bodies it has today.

One decision to make once, before cell.ts is written: whether a failed open is retried on the next demand or cached as a permanent failure. This review chose retry.
