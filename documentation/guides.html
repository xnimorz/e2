Build a small app, one idea at a time

Seven short guides grow one notes app. Each starts from a problem you have probably met, adds one idea, and ends with code you can run. Every code block on this page is cut from a playground example that is type-checked and tested along with the library, so what you read is what runs.

  1. 1Your first serviceDescribe it, implement it, use it, run it.
  2. 2Wire an applicationServices that need services, opened and closed for you.
  3. 3Handle failureExpected errors in the type, bugs kept apart.
  4. 4Test itSwap implementations instead of mocking modules.
  5. 5Open things lazilyOnce, on first use, shared by everyone waiting.
  6. 6Coalesce writesCallers add one note; the disk sees a hundred.
  7. 7Time out, retry, cancelWork that stops when nobody wants it.
Guide 1

Your first service

Run this guide ▸

A service is anything your code needs but should not build itself: storage, a clock, an HTTP client. You describe it once, ask for it where you need it, and decide what fills it at the edge of the program.

  1. Describe what it does.

    An interface says what the service can do. service<Notes>()('Notes') makes the key the program asks for. They share a name on purpose: the type Notes is the contract, the value Notes is the key.

    
      
    2. 
      
  2. Implement it.
        
    Notes.make takes a generator that returns the implementation. Parameter types come from the contract, so text needs no annotation.
    
        
    
      
    3. 
      
  3. Use it.
        
    Inside fx(function* …), yield* Notes gives you the service, and yield* on anything it returns gives you the result. Nobody writes the type on the last line; e2 works out that this needs 'Notes'.
    
        
    
      
    4. 
      
  4. Run it with an implementation.
        
    
      
    5. 
      
  5. Forget the implementation, and see what happens.
        
    Change the list to []. The program no longer compiles, and the message says what is missing:
    
        
    
          
    TS2345run(remember('buy milk'), [])
    
          
    Type 'Fx<readonly Note[], never, "Notes">' is not assignable to type '"e2: missing service Notes"'.
    
        
    
      
    6. 
    

    
What you gotA dependency the compiler knows about. Replace NotesInMemory with a database-backed implementation and nothing that uses Notes changes.

  


  
  

    

      

        
Guide 2

        
Wire an application

      

      Run this guide ▸
    

    
Real services depend on each other. The notes store needs a clock and a logger; the logger needs configuration. Usually that means building things in the right order and remembering to close them. Here each implementation asks for what it needs, and the runtime works out the rest.

    
    
      
  1. Add the contracts.
        
    Same shape as before: an interface and a key for each.
    
        
    
      
    2. 
      
  2. Implement the simple ones.
        
    of takes a value you already have. make is for an implementation that needs other services: it yield*s them. The comment under LoggerLive is its inferred type: it provides 'Logger' and needs 'Config'. Nobody wrote that list down; it comes from the body.
    
        
    
      
    3. 
      
  3. Open resources with acquire.
        
    acquire pairs opening something with closing it. The close runs when the application stops, newest first, whether it stops cleanly or not.
    
        
    
      
    4. 
      
  4. List everything once, in any order.
        
    runtime builds each service the first time something needs it, following the yield*s, and keeps them for as many runs as you like. app.graph() shows what was built and what each one asked for.
    
        
    
        
    Leave ClockLive out and app.run stops compiling:
    
        
    
          
    TS2339runtime([NotesLive, LoggerLive, ConfigLive])
    
          
    Property 'run' does not exist on type '"e2: missing service Clock"'.
    
        
    
      
    5. 
    

    
What you gotNo container configuration, no construction order, no forgotten close(). Adding a dependency to a service is one yield* in its body; the compiler then tells you whether the list still covers it.

  


  
  

    

      

        
Guide 3

        
Handle failure

      

      Run this guide ▸
    

    
Things go wrong in two different ways. Some failures are outcomes you expect: the note does not exist, the text is empty. Others are bugs. e2 keeps them apart: expected failures are part of the type, so the compiler tracks them; bugs are not, so they cannot hide among them.

    
    
      
  1. Name the failures.
        
    A class with a _tag. TaggedError extends Error, so stack traces and instanceof work as usual.
    
        
    
      
    2. 
      
  2. Say which methods can fail, and how.
        
    The second type parameter of Fx lists what can go wrong.
    
        
    
      
    3. 
      
  3. Write checks as plain functions.
        
    ok and err build a Result. No effect, no service: just a function you can call anywhere.
    
        
    
      
    4. 
      
  4. Let yield* stop at the first failure.
        
    Yielding a Result continues with its value, or ends the body with its error. It is the ? operator from Rust, in TypeScript.
    
        
    
      
    5. 
      
  5. Watch the errors add up by themselves.
        
    duplicate calls a method that can fail with NoteNotFound and one that can fail with EmptyNote, so its type says both.
    
        
    
        
    
      
    6. 
      
  6. Recover from the ones you choose.
        
    catchAll sees expected failures only. Return ok to recover, or err to pass the failure on. The type follows: NoteNotFound is gone, EmptyNote remains.
    
        
    
      
    7. 
      
  7. Leave bugs as bugs.
        
    
      
    8. 
    

    
What you gotEvery expected failure is in a signature, so a new one is a compile error at every place that has to decide about it. Bugs reject loudly instead of being caught by a handler written for something else.

  


  
  

    

      

        
Guide 4

        
Test it

      

      Run this guide ▸
    

    
Code that imports its dependencies needs module mocks to test. Code that asks for services needs nothing special: run it with different implementations.

    
    
      
  1. Start from the code you want to test.
        
    It reads the clock and the notes. It has no idea it is under test.
    
        
    
      
    2. 
      
  2. Write doubles as ordinary providers.
        
    A fixed clock is Clock.of(…) with a fixed date. A store with known contents is Notes.of(…). Small functions make them reusable.
    
        
    
      
    3. 
      
  3. Run the same program against different lists.
        
    
      
    4. 
      
  4. Replace only what you need to.
        
    Use the real store and a fake clock. Every other service stays real.
    
        
    
      
    5. 
    

    
What you gotNo mocking library and no module patching. A list that misses a double is a compile error like any other. Prefer make for doubles with state, so each run gets a fresh one; and if nothing in a test waits, runSync runs it without await.

  


  
  

    

      

        
Guide 5

        
Open things lazily

      

      Run this guide ▸
    

    
Some things are slow to open and not always needed: a database, a search index, a whole feature. You want each opened once, on first use, shared by everyone who asks while it opens, and closed at shutdown. And you do not want the code that uses it to know any of that.

    
    
      
  1. Wrap the expensive part in memo.
        
    memo does not run anything. It returns a handle; the first yield* of the handle opens the database, and everything after that reuses it.
    
        
    
      
    2. 
      
  2. Keep whole services out of startup with lazy().
        
    Services are built at startup by default, so a broken one fails fast. lazy(…) in the list opts one out: it is built the first time something asks for it.
    
        
    
      
    3. 
      
  3. Use them as if they were ready.
        
    Three reads arrive together; the database opens once and all three get it. The export service is built only when the export runs.
    
        
    
      
    4. 
    

    
What you gotStartup cost moves to first use without a single if (!opened). If the open fails, the readers waiting for it get the failure and the next read tries again.

  


  
  

    

      

        
Guide 6

        
Coalesce writes

      

      Run this guide ▸
    

    
Saving notes one at a time is easy to write and slow to run. Batching usually means changing every caller to collect notes first. Here the store batches its own writes, and callers keep adding one note at a time.

    
    
      
  1. Give the store a batch.
        
    batch takes an operation over many items and hands back enqueue for one item. Items added in the same moment, or until maxSize, go to one call.
    
        
    
      
    2. 
      
  2. Call it one note at a time.
        
    
      
    3. 
    

    
What you got250 calls, three writes, and nothing lost at the end: whatever is still queued is written when the run's scope closes. When a caller needs its own result back, the DataLoader pattern, use add instead of enqueue.

  


  
  

    

      

        
Guide 7

        
Time out, retry, cancel

      

      Run this guide ▸
    

    
Syncing notes to a server can be slow, can fail, and can become pointless when the user navigates away. Each of those usually gets its own mechanism. Here they are one: a request is an effect, and timeouts, retries and cancellation all apply to effects.

    
    
      
  1. Wrap the request, and pass the signal through.
        
    fromPromise gives the request an AbortSignal and maps a rejection to a typed error. With fetch you would pass the signal straight to it. The playground version uses a stand-in that logs when it is aborted.
    
        
    
      
    2. 
      
  2. Add the policy around it, not inside it.
        
    retry runs the effect again on failure, following a schedule. timeout gives up after a deadline and stops whatever is still running. Both wrap the call; the service does not change.
    
        
    
      
    3. 
      
  3. Cancel, and watch the request stop.
        
    Interrupting a fiber aborts the signal handed to its request. The same happens when a timeout fires or a race is lost.
    
        
    
      
    4. 
    

    
What you gotWork started by something that has given up stops too. Forked work cannot outlive what forked it, and cleanup still runs, so nothing is left half-done in the background.
