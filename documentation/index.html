e2 · overview

Dependency injection and control flow for TypeScript, with nothing else attached

e2 is a re-think of Effect scoped to the two things a program cannot do without: knowing what it depends on, and saying what happens next. No Schema, no Stream, no platform package. It runs on Bun and in the browser with no decorators, no build step and no runtime dependencies. The whole worker of the reference application, application code included, is 57 KB.

Three ideas

Everything in e2 is one of these three things

An effect is a description. Fx<Value, Error, Dependency> is a value that says what to compute, how it can fail, and which services it needs. Building one does nothing. A generator body sequences effects with yield*, and an interpreter runs the tree later, against a set of services, producing a Result.

Dependencies are names, and they are inferred. A service is a contract plus a key. Using it six frames deep with yield* Db puts 'Db' into the effect's type without touching any intermediate signature. Wiring is one flat, unordered list of providers, each built on first demand; a missing one is a compile error that names it.

const getUser = fx(function* (id: string) {
  const db  = yield* Db
  const log = yield* Logger
  yield* log.info(`load ${id}`)
  return yield* db.query(id)
})
// (id: string) => Fx<User, DbError, 'Db' | 'Logger'>

await run(getUser('1'), [DbLive, LoggerLive, ConfigLive])   // order is irrelevant
await run(getUser('1'), [DbLive, ConfigLive])
// Type 'Fx<User, DbError, "Db" | "Logger">' is not assignable to type '"e2: missing service Logger"'.

One cell does the sharing. "Build once, let everyone who asks share it, let a failure be retried" is the same mechanism whether the thing being built is a service, a lazily opened database, or a batch of writes. The runtime keeps one cell per provider; memo hands out anonymous ones; batch collects items into one run. Because it is one implementation, they cannot disagree about joining, failure or teardown.

Quick start

A service, an implementation, a program, a run

The repository is the package: bun install at the root, and import from e2, which resolves to src/index.ts. TypeScript 5.5 or later.

1a contract and its key share a name
import { service, sync, run, fx, type Fx } from 'e2'

export interface Config { readonly url: string }
export const Config = service<Config>()('Config')

export interface Db { query(id: string): Fx<User, DbError> }
export const Db = service<Db>()('Db')   // type Db is the contract, value Db is the key
2an implementation yields what it needs
export const ConfigLive = Config.of({ url: 'postgres://localhost' })

export const DbLive = Db.make(function* () {
  const config = yield* Config            // this is the dependency declaration
  const pool = yield* acquire(() => connect(config.url), (p) => p.close())
  return { query: (id) => sync(() => pool.find(id)) }
})
// Provider<'Db', 'Config', never>
3a program, and the list it runs against
const getUser = fx(function* (id: string) {
  const db = yield* Db
  return yield* db.query(id)
})

const result = await run(getUser('1'), [DbLive, ConfigLive])
// Result<User, DbError>
if (result.ok) console.log(result.value)

// A long-lived process builds the graph once:
await using rt = await runtime([DbLive, ConfigLive])
await rt.run(getUser('1'))

The compile-time diagnostics are tested as a feature: src/tests/diagnostics.spec.ts shells out to tsc and pins the exact wording, so a TypeScript upgrade that degrades a message turns CI red. The type-level proofs behind the design live in spike/.
